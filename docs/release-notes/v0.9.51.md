# Release 0.9.51 — Outbound DTMF: the `send_dtmf` builtin.

Voice agents can now **send** DTMF, not just receive it. A new builtin platform
function, `send_dtmf`, plays a string of keypad digits to the far end of a live
telephone call as **out-of-band** RFC 4733 (`telephone-event`) tones — the
signalling downstream telephony equipment expects, rather than audible beeps
mixed into the speech audio.

## Highlights

### New builtin platform function `send_dtmf`

Add a function with `implementation: "builtin"` and `platform: "send_dtmf"` to a
voice agent and the LLM can key digits during a call — navigating a downstream
IVR ("press 1 for sales"), entering an extension, or keying an account /
reference number into an automated system it has dialled or been connected to.

- **One parameter, `digits`** — a string over the alphabet `0-9`, `*` and `#`
  (max 64). Unlike `transfer`'s `number`, `digits` **may be `generated`**: the
  common case is the LLM keying what it worked out during the call. `static`
  and `metadata` sources are also accepted. RFC 4733 A–D are not supported.
- **Played serially, out of band** — each digit is a discrete RFC 4733
  `telephone-event`, with a gap between digits so the far end registers
  distinct presses. On success the function returns `{ "status": "OK", "detail":
  "sent N DTMF digit(s)" }`.
- **Telephone-only, by design** — on a **WebRTC / browser** session there is no
  telephone leg to signal on, so the function returns a `FAILED` result at call
  time (as it does for an empty or out-of-alphabet digit string). The function
  can still be defined on an agent that also takes browser calls.

See [../send-dtmf.md](../send-dtmf.md) for the full reference and examples.

### Runtime support

`send_dtmf` is available on the **LiveKit** and **Pipecat** runtimes only
(gated by a new `hasDtmf` handler capability; `jambonz:`, `ultravox:` and
`text:` reject it at save time). The out-of-band tone always leaves on the
SIP/RTP leg, but the mechanism differs by runtime:

- **LiveKit** publishes each digit with `localParticipant.publishDtmf`; the
  LiveKit SIP service relays it as `telephone-event` to the phone user.
- **Pipecat** asks the SIP gateway that owns the media leg to emit the tones
  (`POST /v1/calls/{id}/dtmf` on **sipbridge**, `POST /v1/legs/{id}/dtmf` on
  **voiceblender**). The bundled Go **sipbridge** gains an RFC 4733
  telephone-event **encoder** to synthesise the tones itself; **voiceblender**
  asks the external media platform to, mirroring its inbound DTMF path. The
  **Daily** and **FreeSWITCH** gateways do not support DTMF send and return a
  clear "not supported on the active SIP gateway" result.

This complements the existing DTMF **receive** handling (inbound keypad presses
buffered to the LLM, tuned with `options.dtmfTimeout` / `options.dtmfTerminator`),
which is unchanged.
