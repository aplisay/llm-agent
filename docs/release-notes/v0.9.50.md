# Release 0.9.50 — Pipecat agents, multi-agent teams (agent sets, transfers, subagents), MCP tools, WebRTC transfers, warm REFER, inactivity timeout, DTMF input configurable.

A second voice agent runtime (**Pipecat**) lands alongside LiveKit, Jambonz, and Raw Ultravox. 
Browser/WebRTC calls become first-class transfer participants.
Consultative transfers gain SIP REFER finalisation.
DTMF (with configurable termination config), inactivity, and call-recording behaviour are unified across both runtimes.
An optional configurable hold confidence tone is added whilst waiting for all kinds of transfers.
Several SIP gateways and security defaults (TLS, SRTP) also ship, along with a new single-call endpoint and a cursor-pagination-ready call schema.
This release also introduces **multi-agent** groups — agent sets, live agent-to-agent transfers, and headless text subagents — and lets agents expose **remote MCP servers** as tools.

## Highlights

### New `pipecat` agent runtime

A full second voice runtime is now selectable wherever a handler is chosen. `pipecat` is added to the `handler` enum on agent endpoints, phone endpoints, and the listener-deployments list; it is a valid `PhoneNumber.handler` value (`TELEPHONY_HANDLER_NAMES = jambonz, livekit, pipecat`).

The Pipecat model catalogue exposes two model classes via the standard `/models` surface:

- **Realtime (speech-to-speech):** `openai/gpt-realtime`, `google/gemini-2.0-flash-exp`, and Ultravox (`ultravox-v0.6`, `ultravox-v0.6-gemma3-27b`, `ultravox-v0.7`).
- **Pipeline (STT → LLM → TTS):** `openai/gpt-4o-mini`, `openai/gpt-4o`, `openai/gpt-5-mini`, `google/gemini-2.5-flash`, `google/gemini-2.0-flash`, `anthropic/claude-sonnet-4-5`. For pipeline models, `options.stt` and `options.tts` select the per-stage providers; the model name selects the LLM.

Voice/recognition selection is Pipecat-aware: realtime models only offer their own provider's voices, and pipeline models surface a constrained STT provider list (Deepgram) and TTS vendor allow-list (Deepgram, ElevenLabs) through the existing model/locale-scoped voice endpoints.

Invocation logs gain a `pipecat-agent` subsystem value alongside `livekit-agent` on `GET /agent-db/invocation-log`.

### WebRTC / browser calls as transfer participants

Calls that originate from a **WebRTC / browser** participant can now be transferred — both `blind` and `consultative` operations are supported. Because a browser call has no inbound trunk and no SIP dialog, these transfers are always bridged (media relayed inside the worker) and `callerId` is **required**: it must be a number owned by your organisation with outbound calling enabled, whose trunk becomes the egress path. `forceRefer` is ignored for WebRTC participants.

### Consultative transfers over SIP REFER + new `forceRefer` flag

Consultative (warm) transfers are no longer bridging-only. The finalisation hop (connecting the caller to the consulted target) now participates in the automatic bridge-vs-REFER selection, and a new per-transfer flag controls it:

- **`forceRefer`** (boolean, optional): forces a SIP REFER transfer even when the platform would otherwise bridge. Applies to both `blind` and `consultative` operations, only on REFER-capable SIP participants. Takes precedence over `forceBridged` if both are set. Use it to release the call to the carrier and free platform media resources.
- **`forceBridged`** is extended to also cover the consultative finalisation hop (previously blind-only).

These per-transfer flags take precedence over trunk (`forceReferTransfer`) and registration (`bridged_transfer`) endpoint defaults.

### DTMF collection options

Two new agent options give deterministic control over keypad-tone collection (honoured by both the LiveKit worker and the Pipecat worker across all its SIP gateways):

- **`dtmfTimeout`** (integer ms, default `1500`): inter-digit buffering window. Digits accumulate and flush to the model as a single turn once no further digit arrives within the timeout. `0` flushes each digit immediately.
- **`dtmfTerminator`** (string, default `"#"`): an input that flushes the buffer immediately. The terminator is not added to the buffer; set to `""` to disable.

### Inactivity "kick"

New agent option **`inactivity: { timeout, message }`**. When a live call has no conversational activity for `timeout` (a number of seconds or a `"30s"`-style string), the agent speaks `message` verbatim via TTS. It re-fires on each further period of silence and resets on any activity. Omitting it (or an empty `message`) is a no-op. Honoured by both the Pipecat and LiveKit workers, including the Ultravox realtime path. Distinct from the provider-native `vendorSpecific.ultravox.inactivityMessages`.

### Call recording — cross-runtime parity

Call recording is now implemented end-to-end for **both** the LiveKit and Pipecat runtimes against a single shared contract: stereo **OGG/Opus** (user left, agent right), streaming **AES-256-GCM** encryption (`IV ‖ ciphertext ‖ auth tag`), and GCS storage. Client-provided keys (`options.recording.key`) yield encrypted-on-download (client decrypts); server-generated keys yield decrypted raw playable data. The existing `GET`/`DELETE /calls/{callId}/recording` endpoints and `recordingId` field are unchanged on the wire.

### SIP security defaults

SIP transport now **defaults to TLS**, with **SRTP** media encryption and RTP-timeout-driven hangup. Outbound Contact-header protocol selection was corrected.

## Multi-agent agents

Teams of agents can now front a single phone number or room. A live call hands off between agents (same call, no new leg), agents delegate work to headless text subagents, and a whole team is created from one document. The full user guide is [multi-agent-api.md](../multi-agent-api.md).

### Agent sets

A new `/agent-sets` resource lets you create, update, and delete a **group of agents** from a single JSON document, with members able to reference one another by shortform label. See [agent-sets-and-subagents.md](../agent-sets-and-subagents.md) and [multi-agent-api.md](../multi-agent-api.md).

- **`POST /agent-sets`** — creates a set and all its members from an `AgentSetInput` document (`name`, `description`, and a non-empty `agents` array). Returns the full `AgentSet` with member label references resolved to agent UUIDs.
- **`GET /agent-sets`** — summary index. Each set lists members by `id`, `label`, `name`, `modelName`, and `type` only (`AgentSetListItem`); use the by-id endpoint for full definitions.
- **`GET /agent-sets/{agentSetId}`** — the set with full member agent definitions, ordered by `label`. `404` when the set is not found or not visible to the caller.
- **`PUT /agent-sets/{agentSetId}`** — reconciles the set against the supplied document **by `label`**: existing labels are updated in place (member agent IDs stay stable), new labels are created, and members whose label is absent from the document are deleted.
- **`DELETE /agent-sets/{agentSetId}`** — removes the set **and all of its member agents**.

Each member carries a `label` (string, pattern `^[a-zA-Z0-9][a-zA-Z0-9_-]{0,63}$`, unique within the set). Within a member's `functions`, `transfer_agent` and `subagent` builtins may target another member with `{"source": "static", "from": "label:<label>"}`. The platform fixes these labels up to real agent UUIDs on create/update and retains the original as `fromLabel`, so a set document round-trips cleanly through `GET` → `PUT`. A `label:` reference to a non-member is rejected with `400`, as is a target of the wrong agent type — `transfer_agent` must target an `interactive-audio` agent and `subagent` must target a `text` agent.

- **Transactional** — each create/update runs in a single transaction (label fixup, cross-reference validation, then save); it either fully applies or leaves the set unchanged.
- **`keys`** are never included in member responses on any agent-set endpoint.

Schema: a new `agent_sets` table, and `Agent` gains `label` and `agentSetId` columns (unique index on `agent_set_id, label`). The `agentSetId` foreign key cascades on delete.

### Agent-to-agent transfers (`transfer_agent`)

New builtin platform function `transfer_agent` hands a **live** call from one agent to another — same call, no new leg. The caller stays connected throughout; the platform picks the handover mechanism automatically. Supported on `livekit:` and `pipecat:` handlers only — validation rejects it on `jambonz:` and `ultravox:` agents (`Model <modelName> does not support agent-to-agent transfer…`). See [../multi-agent-api.md](../multi-agent-api.md) "What happens on a transfer".

Parameters:

- **`agent`** (string, required): the target agent ID. Must be `static` or `metadata` sourced, **never `generated`** — the same anti-fraud rule as `transfer`'s `number`. A `static` value must be an agent UUID, except inside an `/agent-sets` document where it may be a `label:<label>` reference (fixed up to a UUID on save). The target must be an `interactive-audio` agent in the same organisation — checked both at save and at call time.
- **`includeHistory`** (boolean, optional, `static`, default `false`): when `true`, carries the conversation transcript into the new agent's context. Omitted or `false`, the new agent starts clean. A non-`static` source is rejected.
- **`summary`** (string, optional, `generated`): an LLM-composed handover note, delivered to the new agent alongside its prompt regardless of `includeHistory`.

Two automatic handover modes:

- **In-place handover** — used when the target has the **same `modelName`** and the stack supports the swap. The prompt and tools are replaced inside the live session (LiveKit `llm.handoff()`; Pipecat `LLMUpdateSettingsFrame` / `LLMMessagesUpdateFrame` / `LLMSetToolsFrame` / `LLMRunFrame`). **Same call record**, same model, same voice.
- **Full-stack handover** — used when the **model string differs**, or on Ultravox realtime (Pipecat Ultravox cannot swap prompt/tools after session creation, so even a same-model transfer restarts; LiveKit Ultravox swaps in place only when the tool surface is unchanged and otherwise restarts). The target agent's own model/voice/tool stack starts on the same live call and a **new child call record** is created with the original call as `parentId`; the original ends with status `transferred to agent <id>, continued as call <child-id>`, and transcripts/usage from there log against the child. Prompt-only (in-place) swaps do **not** create a child record.

Constraints on full-stack handover:

- The target model must run on the **same worker** as the live session (`livekit:` ↔ `livekit:`, `pipecat:` ↔ `pipecat:`).
- On Pipecat, full handover runs on the **websocket SIP gateway** legs (FreeSWITCH / sipbridge / voiceblender) and **browser WebRTC** sessions; Daily legs, consultation legs, and calls with an engaged media relay refuse with `FAILED`.
- Call recording does not follow a full handover on LiveKit (recording covers up to the handover); Pipecat records each call-record segment separately.
- A busy target (at its concurrency limit) aborts with `FAILED` and the current agent keeps the call — concurrency is reserved for the child before the running session is touched.

Within a worker, **any** two models can hand to each other (realtime ↔ pipeline, Ultravox ↔ OpenAI ↔ Gemini). A `FAILED` result always leaves the call with the current agent, which can recover gracefully.

### Text agents and subagents

A new agent `type` distinguishes live voice agents from headless text agents. `AgentType` is an enum of `interactive-audio` (default) or `text`. A **`text`** agent has no audio session: it is invoked like a function, runs its own LLM/tool loop, and returns a work product. The type is inferred as `text` from a `text:`-prefixed model name (e.g. `text:openai/gpt-4o`, `text:anthropic/…`, `text:gemini/…`, `text:groq/…`), so the field can be omitted on create. See [../multi-agent-api.md](../multi-agent-api.md) section 2.

- **`result`** (builtin, `platform: "result"`) is a text agent's output contract. The agent terminates its run by calling this function; the `result` function's `input_schema` defines the shape of the returned payload, and the (generated) arguments the agent passes become the invocation result. An agent with no `result` function falls back to returning its first plain-text completion as `{ "text": … }`.
- **`subagent`** (builtin, `platform: "subagent"`) lets a voice agent invoke a text agent like any other tool. The `agent` parameter (the target text agent ID) must be `static`- or `metadata`-sourced, never `generated`; within an agent-set document it may be a `label:<label>` reference. Any further `generated` parameters are forwarded as the subagent's task input, and the subagent's `result` payload is returned to the calling LLM as the function result.

Supported callers (`platform` enum extended with `subagent` and `result`):

- **`subagent`** is accepted on `livekit:` and `pipecat:` voice agents, and may be nested from a `text:` agent. It is rejected on `jambonz:` and `ultravox:`.
- **`result`** and direct invocation are text-agent-only.

**Direct invocation** — `POST /agents/{agentId}/invoke` runs a text agent (org/user-scoped; `404` if not found, `400` if the agent is not type `text`). Body: `input` (object, the task, presented as the opening user message) and `metadata` (object, exposed to `metadata`-sourced parameters). Response: `result`, `complete` (boolean, `true` when the agent terminated normally — by calling its `result` function, or via the plain-text fallback — and `false` when it hit the turn limit without delivering a result), and `transcript` (the internal conversation turns).

Execution is bounded: nesting is depth-limited (`MAX_SUBAGENT_DEPTH = 3`), each invocation is capped at 10 LLM round trips (`DEFAULT_MAX_TURNS = 10`), and the whole call is wall-clock limited by `SUBAGENT_TIMEOUT` (ms, default `60000`), returning `504` on timeout.

**Internal worker endpoints** (shared-token, for out-of-process workers):

- **`POST /agent-db/subagent`** runs a text agent by ID for a voice agent's `subagent` call. Body requires `agentId` and `organisationId` (the tenancy boundary: the target must belong to it); `input`, `metadata`, and `callId` (log correlation) are optional. Returns `result` and `complete`.
- **`GET /agent-db/agent`** returns the full agent row including `keys` (which a worker needs to execute the agent's functions), used e.g. to load a `transfer_agent` target. It is unscoped; pass `expectedOrganisationId` to enforce tenancy — a cross-organisation fetch is refused with `404`.

### Remote MCP servers on agents

Agents gain a new top-level property **`mcpServers`** (sibling of `functions`), an array of remote [MCP (Model Context Protocol)](../mcp-servers.md) servers whose tools are exposed to the model as additional callable tools alongside `functions`. Accepted on writes (`POST /agents`, `PUT /agents/{agentId}`, and as an agent-set member field), and returned on the full agent fetch (`GET /agents/{agentId}`) and the `agent-db` instance fetch. Backed by a new JSONB `Agent.mcpServers` column. The `GET /agents` summary row (`AgentListItem`) still omits it — use the full agent fetch.

Each array entry (`McpServers` schema in [api-doc.yaml](../../api/api-doc.yaml)):

- **`name`** (required, `^[a-zA-Z0-9_-]{1,64}$`): identifier that namespaces the server's tool names.
- **`url`** (required): base URL of the remote MCP endpoint.
- **`transport`**: `streamable_http` (default) or `sse`.
- **`headers`** (optional object): HTTP headers sent on every request. Stored on the agent and returned to clients verbatim.
- **`key`** (optional, `^[a-zA-Z0-9_]{1,64}$`): the `name` of an entry in the agent's `keys` array, used to authenticate. Preferred over inline `headers` for secrets — the `keys` array is never returned by the API.

The **Pipecat worker is the MCP client**. Per call, at session build, it connects to each configured server, discovers its tools, exposes them to the model namespaced as `<server>_<tool>` (sanitised to `[A-Za-z0-9_]`, max 64 chars), and proxies invocations; connections are torn down with the call. Discovery is per call, so tool changes on the remote server are picked up on the next call. A bad or unreachable server is skipped with a warning at setup (failure-isolated) — one bad server never takes the call down.

**Credential resolution.** When a server specifies `key`, the worker resolves the named `keys` entry by its `in` type: `bearer` → `Authorization: Bearer <value>`; `basic` → `Authorization: Basic <value>`; `header` → a custom header named by the key's `header` field; `query` → a query-string parameter named by the key's `name`. An explicit `headers` value takes precedence over a key-derived header. An unknown key name or unsupported `in` type yields no auth (logged) rather than failing the connection.

**Model capability.** `GET /models` and the `Model` schema gain a per-model **`supportsMcp`** flag (`Llm.supportsMcp` defaults to `false`; `Pipecat.supportsMcp` is `true` for all Pipecat-routed models). Other handlers store `mcpServers` but ignore it, so an agent can be moved to an MCP-capable model later.

See [mcp-servers.md](../mcp-servers.md).

### Transfer confidence tone

New agent option `options.transferTone` plays a periodic comfort beep to the caller while a transfer is in flight, so they are not left listening to dead air during dialling or while a TransferAgent consults the target on a separate leg. Set it to `true` for the default tone (a medium-pitched, medium-length comfort beep every ~3 s at low volume), or to an object to tune it. When omitted, `false`, or `enabled: false`, no tone path is constructed and behaviour is unchanged. Honoured by both the LiveKit and Pipecat workers across all transfer mechanisms — bridging, SIP REFER, and the WebRTC worker-side media relay. See [../call-transfers.md](../call-transfers.md).

The tone *shape* is intentionally coarse — `frequency`, `length`, and `volume` are chosen from small fixed sets rather than free-form Hz/ms/amplitude — so the platform can serve pre-generated tones for efficiency later; only the silence timings are continuous. Object fields (all optional; values shown are defaults, validated in [lib/database.js](../../lib/database.js)):

- **`enabled`** (boolean, default `true`) — set `false` to disable without removing the object.
- **`frequency`** (`low` | `medium` | `high`, default `medium`) — tone pitch (`low` ≈ 350 Hz, `medium` ≈ 425 Hz, `high` ≈ 550 Hz).
- **`length`** (`short` | `medium` | `long`, default `medium`) — burst length (`short` ≈ 150 ms, `medium` ≈ 250 ms, `long` ≈ 400 ms).
- **`volume`** (`low` | `medium` | `high`, default `medium`) — tone loudness (`low` ≈ 0.08, `medium` ≈ 0.15, `high` ≈ 0.30 linear amplitude).
- **`gapMs`** (number, default `2750`, range 0–60000) — silence between bursts in milliseconds.
- **`graceMs`** (number, default `1200`, range 0–30000) — quiet time required after either party last spoke before the tone starts or resumes.

Behaviour differs by transfer type:

- **Blind** — the tone plays from the moment dialling starts until the transfer succeeds (SIP REFER completes or bridged media is established) or fails, then stops permanently for that transfer.
- **Consultative** — the tone plays for the whole consultation but only in the gaps where neither the caller nor the agent is audibly speaking; it yields to live conversation and resumes after `graceMs` of silence, stopping when the consultation concludes.

### Tenancy, security & robustness

Cross-cutting hardening lands across both runtimes, the API surface, and the Pipecat k8s deployment. None of these change request/response shapes; they close tenant-isolation gaps and accept previously-rejected inputs.

- **WebRTC egress ownership** — a WebRTC-origin transfer's egress `callerId` (an E.164 number or a registration-endpoint UUID) must be owned by the call's organisation. The Pipecat worker (`CallSession._resolve_webrtc_egress`) enforces this with a conservative org-ownership predicate (`_org_owns`) that mirrors `userOwnsRow` in [lib/scope.js](../../lib/scope.js): both sides must be non-null and equal, so a no-org session never claims a no-org row by coincidence. The registration branch and the E.164 branch now hard-reject; a pool number (org `NULL`) is claimable only transitively through a bound listener `Instance` owned by the same org, and an instance-lookup failure **fails closed**. A rejection surfaces to the agent as a `FAILED` transfer.
- **Endpoint read scoping** — `GET /phone-endpoints/{identifier}` now authorises via `userOwnsRow` (an owner-less caller no longer reads an org-owned endpoint as `200`), and `POST /agents/{agentId}/listen` resolves the agent through `scopeWhereForUser` rather than an unscoped `findByPk`.
- **`transfer_agent` / `subagent` target tenancy** — static agent targets are validated against the caller's tenancy both at **save time** (`validateAgentTargets` on `POST /agents`, `PUT /agents/{agentId}`, and `POST`/`PUT /agent-sets`, with a `lookupAgent` scoped by `scopeWhereForUser`) and at **call time** (the `expectedOrganisationId` query parameter on the internal agent fetch, passed by both workers).
- **MCP credential redaction** — MCP servers may now reference a named credential via **`key`** (the `name` of an entry in the agent's `keys` array, pattern `^[a-zA-Z0-9_]{1,64}$`) instead of an inline token. The secret lives in `keys` (never returned by the API) and is resolved into the request by the worker per the key's `in` type: `bearer` and `basic` → an `Authorization` header, `header` → a custom header, `query` → a query-string parameter. Note that inline `mcpServers[].headers` are still stored on the agent and returned to clients **verbatim** — prefer `key` for secrets.
- **Pipecat k8s WebRTC wiring** — the deployment now exposes the worker's `:8082` HTTP API and WebRTC media properly (new `components/webrtc-do` overlay, `WEBRTC_ICE_SERVERS` config, and `SmallWebRTCConnection(ice_servers=…)`); deployment-only, no code-path behaviour change.

## API changes & robustness

### Calls

- **New `GET /calls/{callId}`** — returns a single call object scoped to the authenticated user / organisation, with `404` when the call is not found or not visible to the caller. Fields returned: `id`, `index`, `agentId`, `parentId`, `modelName`, `callerId`, `calledId`, `startedAt`, `endedAt`, `status`, `recordingId`.
- The legacy **`from` / `to`** aliases are **removed** from the `Call` schema; use the canonical `callerId` / `calledId` fields instead.

### Handlers & endpoints

- **`handler` enums** across `/listener`, `/phone-endpoints`, `/phone-endpoints/{identifier}`, and `/phone-numbers` are now driven from a single source of truth and include `pipecat`. Read-side filters accept `HANDLER_NAMES` (`jambonz, livekit, pipecat, ultravox`); create/update bodies accept the narrower `TELEPHONY_HANDLER_NAMES` (`jambonz, livekit, pipecat`).
- **`POST /listener/{listenerId}/join` and `POST /rooms/{listenerId}/join`** now return accurate status codes: `404` only for a genuinely missing listener, `400` for joining a telephony listener or a missing handler, and `500` with the real error message when `handler.join()` throws — previously all failures collapsed to `404`.
- **`POST /listener/{listenerId}/originate`** now canonicalises an E.164-style `callerId` (e.g. `+44…`) to the stored DB format before lookup, so `+`-prefixed caller IDs resolve correctly. Registration UUIDs are left untouched.

## Schema

The database `schemaVersion` (`lib/database.js`) advances from **36 to 38**, applied by the usual per-table alter-sync and gated by `DB_FORCE_SYNC` (or `NODE_ENV=development`) exactly as before. The upgrade adds, in one step:

- a new **`agent_sets`** table (`AgentSet`, cascade-linked to `Organisation` and `User`);
- three new **`Agent`** columns — `type` (`STRING`, default `interactive-audio`; enum `interactive-audio` | `text`), `label` (`STRING`), and `agentSetId` (`UUID`, foreign key to `agent_sets`, `ON DELETE CASCADE`);
- an **`Agent.mcpServers`** (`JSONB`) column for the remote MCP server list.

## Upgrade notes

- For WebRTC-originated transfers, `callerId` is now **mandatory** and must be an org-owned number with outbound calling enabled.
- If you set both `forceBridged` and `forceRefer`, `forceRefer` wins.
- The default SIP transport is now TLS — verify trunk/endpoint configuration if you relied on the previous default.
- **Schema upgrade**: bringing an existing database to v38 follows the usual rule — set `DB_FORCE_SYNC=true` (or run in `development`) so the alter-sync runs; otherwise a version mismatch is logged and the upgrade is skipped.
- **Text agents** require `type: "text"` plus a `text:`-prefixed model, and should define a builtin `result` function for structured output (without one the agent returns its first plain-text reply as `{ "text": … }`).
- **`transfer_agent` / `subagent`** functions are accepted only on supporting handlers (`livekit:`, `pipecat:`, and `text:` for `subagent`/`result`) — saving one on an unsupported handler is rejected at validation. Full-stack handovers require the target model to run on the **same worker** as the live session.
- **`mcpServers` secrets** should be supplied via `key` (the name of an entry in the agent's `keys` array, never returned by the API) rather than an inline `headers` token, which is stored on the agent and returned to clients verbatim.
- **WebRTC transfer egress** is now ownership-enforced on the Pipecat worker: the egress `callerId` must belong to the call's organisation, or the transfer fails.
